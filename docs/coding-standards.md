# Coding standards

Read this file before you write or review code, and review finished code against it before you call the work done. Read [errors.md](errors.md) before you add or change an error, and [observability.md](observability.md) before you add a recorded number, a log line or a profile counter. [architecture.md](architecture.md) says what the game is and how it is built.

Every rule names its check. A lint rule or a `pnpm` script enforces it, or `judgment` marks it for reviewers. `pnpm check:rules` fails when a named check is not an enabled lint rule or a `package.json` script. It also fails when a `rushline/` or `anti-slop/` rule enabled in `oxlint.config.ts` is not named in this file, [errors.md](errors.md) or [observability.md](observability.md). A new rule ships with its row. No rule has an exemption: there are no allowlists, baselines, or per-file disables, and code that breaks a rule is fixed. The ledger enforces that too. It works out each rule's setting the way oxlint does, preset rules first, then the root rules, then each override in order, and fails when `oxlint.config.ts` sets any rule below `error` in its root rules or in an override, or when a preset override turns off a rule that is otherwise on and no later override for the same files turns it back on. The Ultracite presets turn off `no-empty-function` and `promise/prefer-await-to-then` for test files, so `oxlint.config.ts` turns both back on there. A rule the presets leave off is not part of the standard.

## The checks

`pnpm check` runs the `check` group of `scripts/verify.ts`: formatting, lint, the lint rule tests, this ledger, CSS comments, the TypeScript-only check, the repository roots, the renderer imports, source size, the feature map, the save format, dead code, the perf budgets, types, and tests, in that order, and prints how long each took. `pnpm verify` runs the same group, then the build, then the perf gate, `pnpm perf`. Add `--format json` (`node scripts/verify.ts check --format json`) for one JSON report with each check's command, exit code, duration and the tail of its output when it failed. `node scripts/verify.ts static` runs the group without the tests. CI runs four jobs side by side, once for each pull request update and once for each push to `main`. The `static` job runs `node scripts/verify.ts static` and then `pnpm build` as separate steps, so the Actions page shows which of the two failed without opening the log. `tests (police)` runs the police balance test, `pnpm test --project police`, on a runner of its own, because its 200 races fill every core. `tests (!police)` runs every other test, so the two test jobs together run what `pnpm test` runs. The `perf` job runs `pnpm perf`. Nothing in CI runs `pnpm perf:gpu`, which needs this Mac's GPU; [observability.md](observability.md) lists what each perf command checks.

## Upload and sort only what the frame needs

The renderer runs these paths every frame, so a cost that scales with a buffer's capacity or with each comparison shows up in the frame time. Each rule here was fixed once and then came back.

| Rule | Check | Scope | Exemption |
| --- | --- | --- | --- |
| Game code marks a buffer attribute for upload with `uploadSpan` in `apps/web/src/game/uploads.ts`, passing the span of items that changed or are drawn. It skips an empty span, counts the range in scalar components rather than items, folds any range the renderer has not yet consumed into one, and sets `needsUpdate`. An attribute that has never been drawn needs no mark, because three's first upload sends the whole array. Bikes uploaded their whole instance buffers every frame until `23f110a`, and the traffic fleet then did the same with its matrices and colours. The lint rule requires every assignment to `needsUpdate` on a buffer attribute, other than `= false`, to come right after an `addUpdateRange` call on the same receiver in the same block. It recognises a buffer attribute by syntax: `.instanceMatrix`, `.instanceColor`, any member of `.attributes`, a `getAttribute(…)` result, a binding initialised with `new` of `BufferAttribute`, `InstancedBufferAttribute` or a typed subclass such as `Float32BufferAttribute`, a binding initialised with any of these, and a binding or parameter annotated with one of those classes. Materials, textures, render targets and the shadow map are none of these. The rule cannot see an attribute reached another way, such as through an object field, a destructured binding, a loop variable or a function's result, or an upload forced through `version`; review checks those. | `rushline/ranged-buffer-upload` | `apps/web/src/game/**/*.ts` | None |
| Warm-up compiles every shader program and uploads every texture a race draws, so nothing a player meets mid-race stalls a frame for it. `stageEverything` in `apps/web/src/game/staging.ts` adds a sample of every city material, attaches every weapon in both hands and primes the particle pools for one render through the real pipeline, and anything new a race can draw, such as a pedestrian, a junction or a sponsor board, joins what it stages. A shared shadow-depth material that compiled a new variant at tick 268 stalled a 125 ms frame (`ba109d2`). `pnpm perf:gpu` fails when the WebGL context creates a program or a texture on any frame after the first of B's two Slag Row races. It sees only what those races draw after the start grid, so a resource that only another road or an effect they do not trigger draws passes and is for review. It does not count geometries, because city chunks stream in and hazard pools grow by design, so a geometry first uploaded mid-race, as each weapon's was before `8f6ebfe`, is for review too. | `pnpm perf:gpu` | `apps/web/src/game` | None |
| A comparator passed to `setOpaqueSort` or `setTransparentSort` compares numbers the render item already carries, such as `material.id`, and computes nothing per comparison. three calls it for every pair it compares, every frame. Comparing material uuid strings took 1.5 to 10 percent of the main thread's self time (`009383f`), a `WeakMap` numbering of materials brought a hash lookup back on both sides of every comparison (`f25cd7b`), and `81a7cf7` fixed both by reading three's numeric material id. The lint rule reads the comparator, which must be an inline function, `null`, or a `function` or `const` function declared in the same file, and every same-file function it calls by name, transitively. In them it rejects reading `uuid`, by member or destructuring, and calling `localeCompare`, `get`, `has`, `find`, `findIndex`, `indexOf`, `includes`, `sort`, `toSorted`, `map`, `filter` or `reduce`, including through static computed keys. It also rejects a call by name to anything else the file binds, such as an import, because it cannot read it. It cannot see what a method called on an object does, or other array walks such as `some` or `findLast`; review checks those. | `rushline/numeric-draw-sort` | `apps/web/src/game/**/*.ts` | None |

The inherited Ultracite presets run with type information (`options: { typeAware: true }`), so every type-aware rule they turn on is enforced too, such as `typescript/strict-boolean-expressions` and `typescript/no-confusing-void-expression`. ### Sequencing and composition

`ingest` in `apps/web/src/server/telemetry.ts` is a generator because each step needs an earlier result: it gets the store, reads the body, decodes it twice, reads the clock and saves. A `.pipe` on one yielded step translates that step's failure and stays local to it:

```ts
export const ingest = Effect.fn("telemetry.ingest")(function* ingest(
  request: Request
) {
  const store = yield* TelemetryStore;
  const text = yield* readBody(request);
  const value = yield* decodeJson(text).pipe(
    Effect.mapError((cause) => new NotJson({ cause }))
  );
  const batch = yield* decodeBatchEffect(value).pipe(
    Effect.mapError((cause) => new Invalid({ cause }))
  );
  const receivedAt = DateTime.formatIso(
    DateTime.makeUnsafe(yield* Clock.currentTimeMillis)
  );
  const saved = yield* store
    .save(batch, JSON.stringify({ batch, receivedAt }))
    .pipe(Effect.mapError((cause) => new StoreFailed({ cause })));
  const ack: Ack = {
    batchId: batch.batchId,
    duplicate: saved === "duplicate",
    sessionId: batch.session.sessionId,
  };
  return ack;
});
```

One transformation stays a pipe, as `deadline` in `tools/verify/src/context.ts` does:

```ts
const deadline = Clock.currentTimeMillis.pipe(
  Effect.map((now) => now + Number(values.timeout) * 1000)
);
```

Policy that wraps the whole operation goes after the generator, in `Effect.fn`'s combinator arguments, not in a wrapper function. `deliver` in `apps/web/src/diagnostics/upload/delivery.ts` branches on the status and checks the acknowledgement inside its generator, then passes `Effect.catchTag("UploadFailure", …)` to turn an `UploadFailure` from any step into a retry. `save` in `packages/telemetry/src/jsonl-store.ts` passes `(saving) => gate.withPermit(saving)` the same way. In the same file `jsonlStoreLayer` builds the service with a private `Effect.gen` inside `Layer.effect`; that is construction, not an operation.

When a chain of `map`, `flatMap` or `andThen` carries earlier results into later steps, write a generator so the dependencies show. A pipe that starts branching on outcomes or running further Effects belongs in the surrounding generator. Do not turn one clear transformation into a generator, and do not count combinators.
