# Simulation standards

Rules for `packages/sim`, `packages/track`, `packages/career`, `packages/content` and the tools that drive them. The core rules in [coding-standards.md](../coding-standards.md) apply too.

## Keep each module to its job

| Rule | Check | Scope | Exemption |
| --- | --- | --- | --- |
| Generated data is what its builder makes. The Madrid stretches are regenerated in memory and compared against the committed plan, start pose, pieces, blocks, patches and water. Edit the scene file or the builder, run `pnpm madrid:stretch`, and commit what it writes. | `pnpm check:madrid` | `tools/madrid`, `packages/track/src/tracks/madrid-*` | None |
| Within one `SAVE_VERSION` the encoded career save keeps its structure: its field names, which fields are required or optional, nullability, types, structural literals such as board-note kinds, results and endings, and fixed bounds. `scripts/save-wire.ts` reduces the JSON Schema Effect generates to that structure and refuses any construct it cannot read, so a change in how Effect writes the schema needs adapter support, not a new version. The seven catalogues (bikes, roads, levels, racers, rivals, weapons, officers) only grow: `packages/career/save-format.json` lists each version's IDs, the schema and the registry list the same IDs, and an ID any committed registry listed is never removed. Adding a bike, road, rival, weapon or officer needs no new version: `memory` and `season` rows are optional in the save, and `parseCareer` gives a missing row its blank value. A new tier adds a required `qualified` row, so it changes the structure. A changed structure needs a new `SAVE_VERSION`, agreed with the owner. A committed `fingerprint` or `wireFingerprint` is never rewritten or removed. | `pnpm check:save-format` | `packages/career/src/save*.ts`, `packages/career/save-format.json` | None |

## Keep the simulation deterministic

| Rule | Check | Scope | Exemption |
| --- | --- | --- | --- |
| The simulation, track, career and content modules import only each other, and every import and re-export resolves to one of them. Each of those packages exports its modules through `./*`, and a subpath it maps to `null` is closed to other packages. `packages/sim` closes `./pilot` and `./pilot-*`, so only `stepRace` plans a rider. `race.ts` re-exports `carThreat`, which plans nothing and reads the race, for the boxed test in `tools/road-test`. They read no clock, no unseeded randomness, no browser or Node state, and no Effect, Three.js or loader. State is plain data, and `stepRace` advances it by one 1/60 second tick. | `rushline/deterministic-core` | `deterministicFiles` in `oxlint.config.ts`: the sim, track, career and content rule modules | None |
| The deterministic modules use only the exact members of `Math`: `abs`, `ceil`, `clz32`, `floor`, `fround`, `imul`, `max`, `min`, `round`, `sign`, `sqrt`, `trunc` and the eight constants. ECMAScript lets each engine approximate `sin`, `cos`, `atan2`, `hypot`, `pow`, `**` and the other transcendental functions its own way, and V8 rounds them differently on arm64 and x64, so the lint rule rejects `**` and every other member, including any member added to `Math` later. `sin`, `cos`, `atan` and `hypot2` come from `@racer/track/math`, a port of FreeBSD msun 12.2 that uses only `+ - * /` and `Math.sqrt` ([notices](../../packages/track/THIRD_PARTY_NOTICES.md)), and an integer power is a multiplication. `packages/track/src/math.test.ts` pins their output bits to golden vectors taken from Rust's libm. | `rushline/deterministic-core`, `pnpm test` | `deterministicFiles` | None |
| Randomness comes from the seeded generator in `packages/track/src/random.ts`, and each consumer keeps its seed in state. The lint rule rejects ambient entropy and imports from outside the core; whether hand-written arithmetic is a second generator is for review. | `rushline/deterministic-core`, judgment | `deterministicFiles` | None |
| The named tick, frame, planner and input bodies build no function, object, array, rest or spread container, `new` instance or `subarray` view directly. This covers the body's own syntax, not the functions it calls, so it is not an allocation budget. | `rushline/no-hot-allocation` | `hotBodies` in `oxlint.config.ts` | None |
| A module whose tick-path readers sample a per-metre array names the sampler itself, `const sampleAt = sampleAlong`. Calling the imported `sampleAlong` directly adds enough bytecode that Maglev stops inlining the reader into its caller, so every call boxes its double, which measured 3.3 KB a tick on `reference-v1`. | `pnpm perf` | `packages/track/src/track.ts`, `packages/track/src/districts.ts` | None |
| No `for...of` loop in the simulation or the renderer iterates a zero-argument `.entries()` call, written `list.entries()` or `list["entries"]()`, either directly or through a `const` in the same function that holds that call. Iterating entries builds an iterator and a pair for every element: commit `75ca154` measured about 33 MB of them in the perf stress window from the tick and frame loops, and later changes brought the loops back. Read an array or typed array by index, `list[index]`, and walk a Map, a Set or any other collection with a traversal that suits it. Calling `.entries()` outside a loop, such as `batch.entries().next()`, is allowed, and so are a plain `for...of`, `.keys()`, `.values()` and destructuring. The scope is a file list, not a list of functions, so a new helper or module is covered without registering it, and `scripts/deterministic-scopes.test.ts` fails when a sim or renderer module falls outside it. | `rushline/no-entries-loop`, `pnpm test` | `entriesLoopFiles` in `oxlint.config.ts`: the sim modules in `deterministicFiles` and every file under `apps/web/src/game` | None |
| Every sim, track, career and content module has exactly one role: deterministic rules and data, data codec, or test. The save codecs are the career's I/O boundary. The Madrid corridor schema and reader are the track data ingestion boundary. Both get the Effect rules. Every listed hot body exists, once. | `pnpm test`, `pnpm lint:rules` | `scripts/deterministic-scopes.test.ts`, `rushline/no-hot-allocation` | None |
| A race keeps everything that carries from one tick to the next in `RaceState`. `stepRace` takes the human riders' controls keyed by `RiderId`, checks them, and plans every pilot rider itself, so nothing but the state and the frame changes a tick. A module-level buffer in the simulation holds only scratch that each tick refills before reading it: `flight` in `pilot-jumps.ts`, `carrierBody` in `carrier.ts`, `riding`, `deceleration`, `plan`, `paced` and the five scan arrays in `pilot-corners.ts`, `linePlan` in `pilot-lines.ts`, with its sighting pools and the forecast `outlook` that `createOutlook` in `pilot-forecast.ts` builds. A race restored from a snapshot into a fresh state, or into a state another race has dirtied, or run beside other races, rides on exactly as the same race stepped straight through, and so does one restored in a worker, a fresh Node process or a browser page that has run no tick at all. | `pnpm test`, `pnpm replay:engines` | `apps/web/test/pilot-replay.test.ts`, `apps/web/test/cold-restore.test.ts`, `packages/sim/src/snapshot.test.ts`, `tools/replay` | None |
| The race snapshot has one schema, and the schema is the only thing that counts, writes or restores a byte. `snapshot-members.ts` holds the member codecs; `snapshot-format.ts` and `snapshot-setup.ts` hold the field tables, typed `Fields<Read, Write>` over `keyof Write`, so a field added to `RaceState` without a codec entry, a codec for a field the record lacks, an optional field without an explicit presence codec, a union codec that misses a variant, or a write-only codec in a table that must restore all fail `tsc`. `bytesOf`, `putRecord` and `takeRecord` walk that one table, so a field cannot be written and not restored. The format carries a version word, is little-endian through `DataView`, keeps every float64 bit including signed zero, writes one canonical NaN, names the immutable inputs by a 128-bit setup digest over the compiled track the simulation reads, the police and pacing rules and every rider's profile and bike, and refuses a snapshot whose format, length, rider count, car count or digest differs. Checkpoint N is the state after exactly N completed ticks. The hash covers those same bytes and is a diagnostic, never a vote. | `pnpm typecheck`, `pnpm test` | `packages/sim/src/snapshot*.ts`, `packages/sim/src/snapshot-holes.test.ts` | None |
| The eleven recorded replay races each ride to their own terminal outcome, a finish, a bust or a wreck, in Node, Chromium, Firefox and WebKit, and agree with Node on every tick's snapshot hash, on the tick they end and on the outcome they reach. `TICK_LIMIT` caps a race that never settles, and a capped race fails. Each engine and a second Node process also restore a mid-race checkpoint in a context that has run no tick, before the eleven races run there, and carry on tick for tick with the race the checkpoint came from. | `pnpm replay:engines` | `tools/replay`, `apps/web/test/replay-bundle.ts`, the `replay` job in `.github/workflows/quality.yml` | None |
| The browser reads a race through the deeply readonly `RaceView`, the race itself and not a copy, and changes it only through `RaceRun` and the commands in `packages/sim/src/commands.ts`. | `pnpm typecheck`, `pnpm test` | `packages/sim/src/race-view.ts`, `race-run.ts`, `apps/web/src/game`, `packages/career/src/outcome.ts` | None |
| Fixed ticks, held and repeated keys, replays of the same inputs and races run side by side match tick for tick, and render quality, pixel ratio, pacing, sound and the profiler never change a tick. The eleven replay cases keep two recorded sets in `pilot-replay-baseline.json`, the ride to each race's own outcome and the fixed 7,200-tick ride, and each set's chained digest covers every tick of its own ride, so a set is checked tick by tick. A case's two rides also agree on every tick they share. Re-record a set only once the outcomes are proved unchanged tick by tick, and say in the file's provenance what changed the hashes. | `pnpm test` | `apps/web/test/fixed-tick.test.ts`, `input.test.ts`, `pilot-replay.test.ts`, `render-quality.test.ts` | None |

## Tune the numbers before the model

| Rule | Check | Scope | Exemption |
| --- | --- | --- | --- |
| A bike's handling is its `BikeSpec`. Change numbers there before changing the model. [handling-matrix.md](../handling-matrix.md) lists what each field means, what reads it and which test pins it. | judgment | `packages/sim` | None |
| The tests in `packages/sim` pin the feel: acceleration, braking distance, how hard a bend pushes, which bend cannot be taken flat out, when the crest launches. When a tuning change breaks one, decide whether the feel or the test is wrong, and say which in the commit. | judgment | `packages/sim` | None |
| Steering stays live. A rider who only works the pedals does not get through real bends: with the pilot's throttle and brake and the bars held centred, `tools/handling` counts the bends each course survives against a limit per course, and no course may finish that way. The pilot alone rides every course clean and steers on at least 80% of its corner ticks, and a rider who reacts in a quarter of a second holds the road on the staged Madrid bends at 190 km/h. | `pnpm check:handling` | `packages/sim`, `tools/handling` | None |
