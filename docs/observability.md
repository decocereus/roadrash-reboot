# Observability

Rushline records five things: player events for the funnel, play-test telemetry from testers' browsers, one record per room race, one tape and timing trace per room race, and frame profiles for performance work. Read this file before you add a recorded number, a profile counter or a log line. [coding-standards.md](coding-standards.md) explains the Rule | Check | Scope | Exemption tables, and `pnpm check:rules` checks every Check cell here.

## Player events

Twelve events answer where players stop and when their graphics fail: `game_opened`, `game_ready`, `game_load_failed`, `race_picked`, `room_joined`, `invite_copied`, `room_lost`, `race_loaded`, `race_started`, `race_ended`, `race_again` and `graphics_lost`. `packages/telemetry/src/player-events.ts` is the list. `apps/web/src/diagnostics/player-events.ts` sends them with `navigator.sendBeacon` to `POST /api/events`, and `apps/web/src/server/player-events.ts` forwards them to the EU PostHog project named by the `POSTHOG_PROJECT_KEY` secret. With no key, the route answers 503 and sends nothing. `race_started` and `race_ended` carry the race ID, so they join the race's summary: the room's ID for a room race, and a browser-minted one for a solo race.

Collection is on by default. The menus show a short notice until the player presses Got it, and `/privacy` has the detail. Copy says what is recorded and never calls it anonymous: a stable ID ties a player's events together.

## Play-test telemetry

`apps/web/src/diagnostics` holds the hub, the recorder, the uploader and the device-local settings under `rushline.settings.v1`. `packages/telemetry` holds the wire contract. The collector is `POST /api/telemetry`; [errors.md](errors.md) lists its refusals.

## Race records

Every room race has a random race ID that is not the invite link. `apps/rooms/src/notes.ts` holds the lines the room writes to Workers Logs. `pnpm rooms:read` reads them from Cloudflare, or from a saved log with `--file`, and prints one report per race. `CLOUDFLARE_API_TOKEN` needs permission to read Workers observability. Reading races is the job of the [race-room recipe](../.claude/skills/verify-rushline/features/race-room.md).

Neither wait in a report is load time alone. `readyMs` ("ready after") runs until the room hears a rider's `loaded` message, and `waitedMs` ("waited for riders") runs until the countdown starts, which can be at the readiness deadline. A browser that races from the bar holds `loaded` until its 5 s door moment ends, so a longer wait there may mean slow loading or network delay.

| Rule | Check | Scope | Exemption |
| --- | --- | --- | --- |

| No room note holds a guest name, the room ID or an IP address. A rider is named by its number. A seat's edge (`colo`), its network (`asn`, `network`, the provider's name from Cloudflare) and the `started` note's `roomColo` say where a race's time went, and none of them names a person. | `pnpm test` | `apps/rooms/src/notes.ts`, `apps/rooms/src/host.ts` | None |
| The `ended` note lists every rider who started, including those who left, and says whether each browser's stats arrived, so a missing stats line is a counted fact rather than a guess. | `pnpm test` | `apps/rooms/src/host.ts` | None |
| The room writes a note per race event and never per tick or per message. In the tick loop it only adds to the wake counters. | `pnpm test` | `apps/rooms/src/host.ts` | None |

| Workers Logs removes null values and empty lists from a stored line, so `RoomNoteSchema` reads a missing nullable field as null and a missing list as empty. `pnpm rooms:read` warns about any line with a `kind` that still does not decode, because a report without its `ended` line otherwise reads as a dead room. | `pnpm test` | `apps/rooms/src/notes.ts`, `tools/rooms/src/read.ts` | None |

## Race traces

Per-race counters cannot show whether a browser stall and a transport burst happened together, or whether two riders missed controls at the same moment. So the tape folder also holds a timeline per rider. Each browser with Race data on keeps a row each 250 ms: the time, the last room tick it heard, its frame count and worst frame, the ticks it heard and the worst gap between them, its worst round trip, and its held and doubled clock steps. It sends its finished rows every 15 s and the rest when its race ends or it leaves, with its loaded build, graphics card and quality rung, and the room saves them as `rider-<n>.trace.json` when the seat's socket closes or the race ends. Each row's time counts from the start of its own connection, so the file keeps one row list per connection under `connections`, and a rider who rejoined has two. A browser that dies or loses its link loses at most the last 15 s. The room adds `room-trace.json`, which lists each rider's missed and late controls every 15 ticks. Room ticks are the shared clock, so `pnpm rooms:trace --dir <folder>` places each connection on the race clock by its own ticks and lines the riders up by second and counts stalls, tick gaps and misses in the same second. A tick gap with no stall within a second points at the network. A tick gap next to a stall points at the browser, because a stalled browser reads its socket late, and the two can land in neighbouring rows.

## Race tapes

A tape holds enough to run a room race again and check it against what happened. It lives in the `RaceTapes` R2 bucket under `tapes/<race ID>/`, so the race ID joins it to the race's notes and to `race_started` and `race_ended`. `header.json` has the build, seed, seats, road and setup digest. Each `00000.bin` part holds up to 1800 tick packets, about 30 seconds, each with a two-byte length in front. `end.json` has the part count, the last tick and the hash of the state the race ended on. A tick packet already carries every accepted control, every handover and a state hash each 60 ticks, so the tape stores no state snapshots. `pnpm rooms:replay --dir <folder>` rebuilds the race from the header, steps it through the packets and compares every hash, then checks that it stopped on the last tick in the state `end.json` names. The [race-room recipe](../.claude/skills/verify-rushline/features/race-room.md) has the download steps.

| Rule | Check | Scope | Exemption |
| --- | --- | --- | --- |
| A replay fails unless the code builds the same setup digest, every tick follows the last and every hash matches, so a changed control, another build's rules or a missing part cannot read as a match. Replay a tape on the build its header names. | `pnpm test` | `packages/sim/src/room-tape.ts`, `tools/rooms/src/replay.ts` | None |
| In the tick loop the writer only copies a packet into a buffer it allocated at the start of the race. It allocates a part every 1800 ticks. The room's perf run writes a tape, so `room.tick.p95` and `room.allocatedBytesPerTick` include this cost. | `pnpm perf` | `packages/sim/src/room-tape.ts`, `tools/perf/src/node-room.ts` | None |

| A lifecycle rule on the bucket deletes each object after `TAPE_KEEP_DAYS`, and the bucket holds nothing but tapes. Every race is taped during the closed test. Sampling to 1% plus incident captures comes before public launch. | judgment | `apps/rooms/src/race-server.ts`, `apps/rooms/src/tape.ts` | None |
