# Race room

A race room runs one race for up to eight humans on the `RaceServer` Durable Object in `apps/rooms`. It holds WebSocket seats, steps at 60 Hz and sends every seat each tick. A browser joins with `/?room=<room id>`. `pnpm rooms:race` races scripted seats through the same `openRoomSeat` client the browser uses, each one a real `createRoomClient` over a real WebSocket that predicts, rolls back and compares hashes with the room.

## Sub-features

- `tick-rate` holds 60 Hz: a seat's arrival gaps sit near 16.7 ms and it confirms at least 97% of the expected ticks.
- `agreement` keeps every seat on the room's race: `digestMatched` is true and `desyncs` is 0 with `hashesCompared` above 0.
- `no-missed-inputs` gets a seat's controls in on time. `missed` in the status counts the ticks the room stepped with no control from that seat, and it is 0 or close to it on a local link. `pnpm rooms:race` fails when a seat misses over 2% of the ticks. `late` counts every copy of a control that arrived after its tick, and a batch resends up to 8 controls, so it overstates what a rider loses.
- `seat-refusals` sends a ninth seat `refused` with `full` and a seat after the start `refused` with `racing`, and answers a plain request to a seat with 426 and a malformed room ID with 404.
- `own-room` gives each room ID its own room: another room ID reads as a waiting room with no seats while this race runs.
- `dropped-seat` hands a closed seat to the pilot while the others ride on.
- `vanished-seat` drops a seat the room has heard nothing from for 10 s, as a friend losing Wi-Fi looks, writes its `left` line, and the others ride on.
- `lobby-stays-awake` starts a race after the lobby sat longer than the 10 s a Durable Object needs to hibernate. Its fill and deadline timers keep it in memory.
- `fair-start` holds the countdown until every seat has loaded the race, for at most 20 s, so a slow browser does not miss the start. A seat reads `Loading the race` until then.
- `lobby-names` lists the humans in the lobby by name, with any fill as `and <n> more`, so a rider can see a friend arrive.
- `race-tape` saves every race's packets to R2, and `pnpm rooms:replay` runs the race again and matches every state hash.
- `race-trace` saves each browser's timing timeline and the room's missed controls next to the tape, and `pnpm rooms:trace` lines them up by second.
- `lobby-fill` raises a lobby's rider count toward the field of 10 and starts the race at its 2 minute deadline if nobody presses Start.
- `requeue` moves every window to `<id>-r1` when a room dies mid-race, and that room starts from the line by itself.
- `friends-link` opens a new room from `Race friends` on the bar. `Copy the link` copies a URL that seats a second window in the same room.
- `guest-names` asks for a name once per browser, keeps it in `rushline.guestName.v1`, and shows each human's name on the other humans' result sheets in place of a field name. The server cleans every name, so a tampered URL cannot send markup or more than 12 characters.
- `room-logs` writes a few lines per race instead of one per message, because a log event costs far more than the message it records.
- `race-id` gives each race a random ID, separate from the room's invite link, shared by every seat. `pnpm rooms:race` fails when the seats disagree.
- `race-report` turns one race's log lines into a readable report with `pnpm rooms:read`.
- `load-test` runs real seats against many rooms, with load recorded and a message cap on the real network, and reports how many rooms one thread holds.
- `rematch` moves a rider who presses `Race again` on room results to `<id>-m1`, a normal lobby that waits for Start. A rider still on results reads who is waiting there, and loses `Race again` once it has started. `Continue` goes back to the bar with no room in the URL.
- `net-line` prints round trip, rollbacks, resimulated ticks per second and input to frame on room results. `globalThis.__rushlineRoom.report()` returns the same numbers mid-race.
- `race-end` ends the race and closes every seat with 1000 once every rider is done.
- `time-limit` hands every seat to the pilot at six minutes, so a rider who stops and leaves the tab open still gets a result and the room ends.
- `browser-race` puts two windowed browsers in one race, each riding its own bike, with the other human on its road.

## Entry points

- `RUSHLINE_WEB_PORT=<port> RUSHLINE_ROOMS_PORT=<port> pnpm exec alchemy dev --stage verify` runs the Worker in local workerd with no Cloudflare login. Use free ports from 1420 up, never 1350 or 1351.
- `pnpm rooms:race --url <rooms url>` races scripted seats and fails on any problem it lists.
- `pnpm rooms:load --url <rooms url> --rooms 2,4,8` finds how many rooms one thread holds. `pnpm rooms:lag --listen <port> --target <port>` puts a slow, lossy link in front of a room.

## Recipes

Start the Worker and leave it running. `pnpm rooms:race` prints one JSON report and exits non-zero with its `problems`.

- **Tick rate, agreement, inputs, refusals, own room, dropped seat.** Run `pnpm rooms:race --url http://127.0.0.1:<port> --seats 8 --seconds 25 --drop-at-seconds 20`. `problems` is empty. Seven reports show about 1,500 `ticks`, the eighth stops near 1,200 with `closeCode` 1000, `status.seats` lists seven riders each with `late` 0, and `worstBehindTicks` is 1 or 2.
- **Vanished seat.** Put a TCP proxy in front of the rooms port that keeps the upstream socket open and silent when its client dies, seat one scripted rider through it and one directly, start, then `kill -9` the proxied rider. Within about 11 s `curl <rooms url>/rooms/<id>` reads `waiting` 1, the log has a `left` line for that rider, and the other rider's `missed` stays 0.
- **Lobby stays awake.** Run `pnpm rooms:race --url http://127.0.0.1:<port> --seats 2 --seconds 10 --lobby-seconds 12`. `problems` is empty, which shows the sockets and timers survived past the hibernation window.
- **Lobby fill.** Open one window on `/?room=<id>` and leave it. The rider count climbs about every 13 s, and `Rolling out in <n> s` counts down. At 0 the race starts with no key pressed. `curl <rooms url>/rooms/<id>` reads `waiting` 1 throughout the lobby, so the climb is bots.
- **Dead room.** Start a two-window race, then restart the Worker with `touch apps/rooms/src/worker.ts` under `alchemy dev`. Both windows load `/?room=<id>-r1`, read `The last room dropped`, and start a new race from the line within about 8 s, with `digestMatched` true and tick counting up from 0. A window whose socket hangs with no close does the same after 5 s of silence.
- **Race end.** Run `pnpm rooms:race --url http://127.0.0.1:<port> --seats 2 --seconds 400`. It takes a few minutes. Both reports show `ended` true and `closeCode` 1000, and `status.phase` is `waiting`.
- **Fair start.** Start the Worker, put a TCP delay proxy in front of the rooms port for one window through `VITE_ROOMS_URL`, seat both windows, and wait for the first window to reach the name screen before opening the second, because two Vite servers starting together can leave a page on the boot screen. In the slow window run `setTimeout(() => { const t = Date.now(); while (Date.now() - t < 6000); }, 150)`, then `rv click --run <other> "Start the race"`. The other window reads `Loading the race` for those 6 s and neither window reports `predicted.tick` above 0 until about 9 s after the click. `client.confirmed.tick` is 0 at each window's first predicted tick. A window on a 350 ms link goes green about 170 ms before a window on a local link, because its controls for tick 1 must leave earlier to reach the room in time.
- **Room logs.** On the deployed Worker, `GET /accounts/<id>/workers/scripts/<rooms script>/settings` shows `invocation_logs` false. After a race, the rooms Worker's events in Workers Logs are a few JSON lines per race: `started` with the race ID, build, road, seed and digest, `countdown` with `waitedMs` and the rider numbers in `stillLoading`, `left`, `refused`, one `stats` line per rider from the browser, sent when the rider finishes, crashes out, leaves or closes the tab, with no line from a dropped connection, and `ended`, which sums up every rider who started. There are no per-message events and no names.
- **Race report.** Under `alchemy dev`, save the output to a file and run `pnpm rooms:race` against it, then `pnpm rooms:read --file <log> --last 1`. It prints the race ID, the build, the lobby and load times, how many browsers reported, the gaps between wakes and each rider's numbers. For a deployed race, set `CLOUDFLARE_API_TOKEN` and run `pnpm rooms:read --last 3`, or add `--race <race id>`. To test the build label, start `alchemy dev` with `RUSHLINE_BUILD=<any text>`, and the report names it.
- **Race tape.** Under `alchemy dev`, run a race with `pnpm rooms:race`. The local bucket is under `.alchemy/local/r2`, where the `_mf_objects` table of its SQLite file maps each `tapes/<race ID>/` key to a file in `blobs/`. Copy `header.json`, the `.bin` parts and `end.json` into one folder under those names. For a deployed race, get the bucket's name from `cf r2 buckets list`, list the keys under `tapes/<race ID>/` with `cf r2 objects list`, and save each one with `cf r2 objects get`. Then run `pnpm rooms:replay --dir <folder>`. It should print `All <n> state hashes match`, and each rider's mode, finish tick and road should equal the `ended` note from `pnpm rooms:read`. Check out the build the header names first, because other rules refuse the tape. If a part failed to save, the replay names the missing part and fails, and the raw log has a `tapeLost` line with its key.
- **Race trace.** Run a real browser race, because scripted seats draw no frames and send no trace. Download the race's folder as in **Race tape** and run `pnpm rooms:trace --dir <folder>`. It should name each rider's build, graphics card and quality rung, count stalls and tick gaps, and list the bad seconds. `pnpm rooms:read` shows the same browser line and the frame count, p50, p95 and p99 for that rider. With Race data off, that rider has no `rider-<n>.trace.json` and no browser line.
- **Capacity.** Find workerd's own port, because the port in `RUSHLINE_ROOMS_PORT` is a dev proxy that skews the numbers: `pgrep workerd`, then `lsof -a -p <pid> -iTCP -sTCP:LISTEN`, and curl each port's `/rooms/probe` for `catchUpWakes`. Run `pnpm rooms:load --url http://127.0.0.1:<port> --rooms 12,16,20 --seats 8 --full-seats 0`. Each step prints one JSON line with `counted`, `held`, `problems` and the load. A step with `counted` false says nothing, so run it again on a calm machine. The last line gives `mostHeldRooms`.
- **Real network.** Show the owner `pnpm rooms:load --url <deployed url> --rooms 8 --seats 4 --seconds 60 --most-messages <cap> --plan` first. Any run on Cloudflare needs the owner's approval, because the account also runs Faceless. Without `--plan` it runs and stops at the cap.
- **Bad network.** Run `pnpm rooms:lag --listen 1439 --target <workerd port>`, then `pnpm rooms:race --url http://127.0.0.1:1439 --seats 4 --seconds 30`. `desyncs` stays 0 and only the `missed` problems may appear. For a look, start the windows with `VITE_ROOMS_URL=http://127.0.0.1:1439` and read `globalThis.__rushlineRoom.report()`.
- **Time limit.** Open one window on `/?room=<id>`, name it, press `Start the race` and touch nothing. `curl <rooms url>/rooms/<id>` shows `tick` climbing while the bike sits still. At tick 21,600 the bike rides off by itself, `client.stats.rollbacks` does not jump, and the result sheet appears when the pilot finishes, within about 10 minutes of the start. The status then reads `waiting` 0.
- **Two browsers.** Export `VITE_ROOMS_URL=http://127.0.0.1:<rooms port>`, then run `rv up --dev --path "/?room=<id>"` twice with the same `<id>`. `curl <rooms url>/rooms/<id>` reads `waiting` 2. `rv click --run <first> "Start the race"` starts both. Hold `ArrowUp` in each. `globalThis.__rushlineRoom` in each window has `digestMatched` true, a different `me`, and `client.stats.desyncs` 0, and `curl <rooms url>/rooms/<id>` shows `late` 0 for both seats. Two screens at the start look alike, so prove the camera: hold `ArrowLeft` in the window with `me` 0 until its bike crosses the centre line, then `rv shot` both. Each screen centres on the bike at that window's own `client.predicted.riders[me].x`, and the second window, with `me` 1, must not show the bike that crossed.
- **A friend's path.** On a window at `/`, `rv click --run <first> "Race friends"`. Set `#guest` with the native value setter, send an `input` event and `rv click --run <first> "Ride"`. `rv click --run <first> "Copy the link"` reads `Link copied.` Open a second window on that URL and name it. `curl <rooms url>/rooms/<id>` reads `waiting` 2, and the two windows read the same rider count.
- **Names and the net line mid-race.** After a start, hold keys in each window with `rv press`. `globalThis.__rushlineRoom.report()` in each window has the other human's name under the same slot, `samples` equal to the presses that changed a control, and `medianMs` of one or two frames.
- **Names on results and a rematch.** Run both windows with `&autopilot` until `document.body.innerText` includes `ROUND TRIP`, which is uppercase because the page styles it so. Each sheet lists `You` and the other window's name. `rv click --run <one> "Race again"` puts that window on `<id>-m1`. Within 3 s the other window reads `<name> is waiting in the rematch`, and `Race again` there puts it in the same lobby, which reads `waiting` 2 and does not start by itself. In a second run, press `Start the race` in the lobby instead. The window still on results reads `The rematch has started without you` and no longer offers `Race again`.
- **A finish in the browser.** Add `&autopilot` to both windows. A window with `autopilot` sends no controls, so the room's pilot rides that seat and the window shows the confirmed race. After about 3.6 minutes each window shows the finish banner for its own rider.
- **Host rules without a Worker.** `pnpm exec vitest run --project node apps/rooms` drives `host.ts` with a fake clock: packets, hash agreement, refusals, the four-tick catch-up, leaving and race end.

Reading the numbers: `rollbacks` and `resimulatedTicks` count every remote steer change the client guessed wrong, so scripted weaving seats roll back several times a second by design.

## What this does not prove

- A deployed room. Cloudflare's scheduling and `locationHint` placement are untested here. Point `--url` at the deployed Worker to test them.
- Real network lag, jitter or loss. A local link hides lag, and a clock that led by half the round trip passed every local run. A throwaway TCP proxy adding 100 and 200 ms round trips gave `late` 0 and 0 desyncs, and that clock lost every control at 100 ms. No lag tool is checked in yet.
- How a rollback looks over a real network. On a local link the other rider's largest frame-to-frame sideways move was 7.1 cm over 88 rollbacks.
- That a slow window makes the requeue. A window that reloads later than the 8 s start reads `This race has already started`.
- Public Quick Race matchmaking. Rooms are joined by link only.
- Input to screen. `Input to frame` runs from the key event to the start of the frame after the one that drew the change. It does not include the compositor or the display, and a gamepad has no key event, so a gamepad rider reads 0 samples.
